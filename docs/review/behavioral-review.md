## 0. 一句话结论

产品把一个**生产性决策**（我要不要给我的 agent 装一个新能力）包装成了一个**消费性浏览**
（刷卡片），但奖赏留在了产品外面（GitHub）。这个错配本身可以靠设计弥补，
真正致命的是：**弥补所需的行为回路一条都没接通**——
反馈按钮不产生可感知后果、身份页全是空态、离站后没有任何回流触点、
而唯一能验证"用户真的装上了"的资产（skill-picker 的本机 scan）没有被接进来。

## 1. 发现清单

严重度定义：**P0** = 不修则核心动机链条在第一次会话内就断；**P1** = 显著削弱留存/复访；
**P2** = 影响信任与观感，可排在后面。

### 1.1 核心动机链条

#### F-1 · P0 · 主 CTA 不在首屏，卡片没有"一屏一卡"

**证据**（16:47，390×844 视口）：第一张卡 `top=351px`、`height=650px`；
`「打开 GitHub」` 的 `getBoundingClientRect().top = 950px`，视口高 844px。
即**用户进入页面后，在不滚动的情况下永远看不到主行动按钮**。
顶部 chrome 吃掉 351px：logo/语言开关 + 搜索框 + 提示条 + Stories 圆环 + 一级筛选条 + 二级筛选条。

同时 `scroll-snap-type` 在 `document` / `body` / `.post` 上全为 `none`
（CDP 实测），`.shell` 与 `.feed` 的 `overflow-y: visible`。
**这不是抖音式竖向流，是普通网页长列表。**
滚到 760px 的截屏里（`feed-scroll-760.png`）同屏出现两张卡的碎片：
上一张的 `score` 行 + `打开 GitHub` 按钮，紧贴着下一张卡的作者行和标题。

**行为机制**：Fogg 行为模型 `B = MAP` 中，Prompt（提示）必须与 Motivation 峰值**同时出现**。
用户读完亮点、动机刚起来的那一刻，按钮不在视野里；等他滚出按钮，视野里已经是下一张卡的标题了——
提示与动机被空间错位打散。抖音之所以有效，恰恰因为它用**吸附 + 固定右侧操作轨**
保证"内容单元"与"行动入口"永远同屏共现。这里两者都缺。

**方向**：卡片高度必须收进一屏可视区（或让主 CTA 随当前卡吸附常驻）；
顶部 chrome 在滚动时应让位；筛选条与 Stories 不该和内容抢首屏。

#### F-2 · P0 · 反馈按钮不产生任何可感知后果（"谎言按钮"）

**证据**：`feed_dashboard.py:2506-2510`

```2506:2510:feed_dashboard.py
  if (t.closest('.js-bad')) {{
    sendFeedback('bad', itemPayload(card));
    toast(tr('notUsefulToast'));
    return;
  }}
```

toast 文案是 `'已记下，之后少推这类'`（`:775`）。但这个 handler：
不移除卡片、不写 `localStorage`（`loadSet` 只有 `sf_liked` / `sf_saved` /
`sf_follow_builders` / `sf_follow_industries`，**没有 disliked 集合**，`:891-894`）、
不改动 `filtered()` 的结果、不触发 `render()`。
负反馈唯一的去处是 `rank.py:151` 的 `load_feedback_affinity()`，
而它在**构建期**（`build`/`refresh`）读 `feedback.jsonl` 算 `repo_penalty` 并写进 `feed.json`。
也就是说"少推这类"最快要等到下一次 6 小时刷新才生效，且当前会话内 100% 无效。

**行为机制**：操作性条件反射的**强化即时性梯度**——强化物延迟数秒即显著减弱学习，
延迟 6 小时等于零。更糟的是这构成 Langer 的**控制错觉**被主动打破：
用户按下按钮、系统承诺"记下了"、下一屏出现同一个 `larksuite/cli` 的第 5 条卡。
一次即可完成**期望违背**，两三次后进入**学得性无助**，此后用户放弃全部反馈控件——
连带把还算正常的点赞/收藏一起毁掉（信任是按控件族群整体崩塌的，不是单个按钮）。

**方向**：负反馈必须在**同一帧**产生可见后果（最低成本的是当前列表内立即隐去该条 + 可撤销）；
承诺文案的时间尺度必须与实际生效尺度一致，不能用"之后"掩盖"下次重建"。

#### F-3 · P0 · 反馈信号在线上根本没有落地通道

**证据**：
- 前端 `sendFeedback()`（`:1519-1533`）把请求写死为 `fetch('/api/feedback')`，
  没有走同文件里已有的 `apiUrl()`（`:1224`）。
- 本机 `skillfeed.py serve` 的 `FeedHandler` 有 `POST /api/feedback`（`skillfeed.py:845-858`）→ 能写盘。
- **线上 FastAPI（`server/app.py`）没有 `/api/feedback` 路由**（全目录 grep `feedback` 零命中）。
  线上暴露的写接口只有 `/api/posts` 与 `/api/posts/{id}/react`，两者都要求登录。
- 单文件 lite 版从 `file://` 打开时，该 fetch 必然失败（且失败被 `catch` 静默吞掉）。
- `~/.skill-feed/feedback.jsonl` 共 **5 行**，全部产生于 **2026-07-27 10:20–10:56 UTC**，
  动作分布 `useful:3 / opened_github:2`，**bad 一条都没有**。此后 5 周多零新增。

**行为机制**：这不是一个 UI 问题，是**反馈回路（feedback loop）的四个环节（证据→关联→结果→行动）
里第一环就断了**。产品的全部个性化能力（`rank.py` 的 `scene_boost` / `repo_penalty` /
`repo_boost`）都建立在一个从未被写入的文件之上。
对用户侧的直接后果：产品**永远不会"越用越懂我"**，而竖向流品类的复访理由几乎全部来自这一条。

**方向**：先把通道打通再谈排序权重；线上/lite/本机三种形态需要各自明确的信号落点，
lite 版收不到就不该显示"已记下"这类承诺文案。

#### F-4 · P1 · 卡片上暴露内部排序分与漏斗调试信息

**证据**：
- `feed_dashboard.py:1685`：`<div class="likes">★ ${{stars}} · score ${{score}}</div>`。
  截屏（16:39）第一张卡底部是 `★ 16,729 · score 1.54`，第二张 `★ 173,323 · score 1.31`。
- 搜索无结果空态实际渲染出（16:52，关键词「织毛衣」，见 `feed-empty-search.png`）：
  `漏斗：trending 19 · search 40 · 过门禁 374 · rejected {"G_source":0,"G_star":0,"G_rel":0,"G_parse":81}`
  （`:1896-1897`），原始 JSON 直接落在用户视线里。

**行为机制**：`score 1.54` 是一个**无锚点数字**——用户不知道满分、不知道方向、
不知道 1.54 比 1.31 好在哪。行为经济学里无锚点的量化信息不产生偏好，
只产生**归因焦虑**（"是不是给我看的是低分货？"）。
而 `rejected {...}` 这种把内部质量门禁的失败计数展示给用户的做法，
等于在最脆弱的时刻（搜索扑空）主动坦白"我们抓来的东西 81 条解析失败"，
削弱的是**能力型信任（competence trust）**。

**方向**：内部分值与门禁统计属于运营视图，不属于消费视图；
如果要保留可解释性，展示的应是用户能理解的理由（"因为你看过…"已经在做了，那条留着就够）。

#### F-5 · P1 · 社会证明失真：97% 的卡片共享 star 数

**证据**（`feed.json`，17:00 统计）：
- 388 条卡片，只对应 **57 个仓库 / 55 个 owner**。
- 单仓库上限 20 条：`sickn33/agentic-awesome-skills` 20、`mattpocock/skills` 20、
  `larksuite/cli` 20、`microsoft/azure-skills` 20、`affaan-m/ECC` 20、`aeonfun/aeon` 20、
  `addyosmani/agent-skills` 20、`vivy-yi/xiaohongshu-skills` 20、`alinaqi/maggy` 20、
  `bytedance/deer-flow` 19、`antfu/skills` 18、`anthropics/skills` 16 …
- star 是**仓库级**的，被原样赋给每个子 skill：`anthropics/skills` 的 16 张卡全部标 `173,323`，
  `affaan-m/ECC` 的 20 张全部标 `246,534`，`larksuite/cli` 的 20 张全部标 `16,955`。
- **388 张卡中 378 张（97.4%）的 star 值与至少一张其他卡重复**；另有 **56 张 `stars=None`**，
  界面显示 `★ —`。
- 顶部作者行、中部 Stats 区、底部 likes 行**三处重复展示同一个 star**（截屏 16:39）。

**行为机制**：Cialdini 的社会证明依赖**可区分性**——当 20 个不同条目挂同一个数字，
这个数字就从"质量信号"退化为"品牌背景色"，判别力归零。
更危险的是它是**可被用户亲手推翻的**：任何人连续滑过 3 张 `anthropics/skills` 的卡
就会发现星数一模一样，此刻他不会只怀疑 star，他会怀疑整张卡是不是都在复用模板
（第二张卡的 tagline 正是仓库级的 `Public repository for Agent Skills`，
挂在名为 `internal-comms` 的子 skill 上）。信任一旦从"数据可能是套的"开始，
就再没有便宜的修复办法。

**方向**：子 skill 卡需要 skill 级的质量信号（哪怕是"来自 173k★ 仓库"这种明确的归属表述，
也远好于把仓库星数伪装成条目星数）；`stars=None` 的 56 条要么补齐要么换轴。

### 1.2 首次体验与冷启动

#### F-6 · P0 · 前 3 张卡没有完成任何心理任务

前 3 张卡应当依次完成：**这是什么**（品类识别）、**为什么和我有关**（自我关联）、
**下一步做什么**（行动可得性）。实际情况：

- **品类识别失败**：进入页面第一眼是 6 条 chrome（logo、搜索框、提示条、两个空圆环、两条筛选条），
  第一张卡的标题是 `hardikpandya/stop-slop`，副标题是英文 `A skill file for removing AI tells from prose`
  （中文界面下未译，`one_liner_zh` 字段存在但 tagline 位用的是 `description`）。
  一个从小红书点进来的内容创作者，在这一屏得不到"这是给我的 AI 助手装能力的地方"这个认知。
- **自我关联失败**：排序结果的前 12 条 `scene` **全部是 `content`**（`feed.json` 实测），
  而库存里 `engineering` 占 132/388（34%）。`rank.py:326-330` 的 `rerank` 只按
  `personal_score` 降序，**没有任何行业/owner 多样性约束**（这一条设计文档已规划，代码里还没有）。
  结果是任何一个工程向用户在前 12 卡里看不到一条属于自己的内容。
- **行动可得性失败**：见 F-1，主 CTA 不在首屏。

**行为机制**：首次体验的任务是建立 Fogg 模型里的 Ability——
让用户在最低认知成本下完成一次完整的"看懂→关联→行动"。
现在三步全在前 3 卡内失败，而竖向流品类的首会话流失窗口通常只有 5–8 次滑动。

**方向**：前 3 卡应当被当作 onboarding 资源来编排（品类锚定 / 高普适性 / 强行动闭合），
而不是交给通用排序；行业多样性配额在首屏就该生效。

#### F-7 · P1 · 两条提示条是"产品自述"，不是用户教育

**证据**（`:668-670`、`:771-772`）：
- `liteBanner`：「**本机没有合适 skill 时**，在这里按意图浏览远程线索，
  点「打开 GitHub」自行安装；装好后回 skill-picker 再扫一遍。」
- `storiesHint`：「**顶部圆环 = 你关注的最新动态**：关注 Builder 或行业后，新内容会出现在这里优先观看。」

16:39 截屏中实际显示的是 `storiesHint`（占 2 行、约 25px），可 `×` 关闭
（`sf_stories_hint_dismissed`）。`liteBanner` 只在 lite 变体显示。

「我的」页面还有第三条同类文案（`:1953`）：
「Stories = 关注动态；下方 pills = 逛发现时的行业/栏目筛选。**两者不再重复**。」
——"不再重复"是一句修 bug 的开发备注，被写进了用户界面。

**行为机制**：这三条都在解释**机制**（圆环是什么、pills 和 Stories 的区别），
而用户在第一次会话里需要的是**结果预期**（我在这能得到什么）。
解释机制属于 Nielsen 说的"文档补偿设计"：当界面自身无法自解释时用文字打补丁，
成本是把工作记忆预算（本就要用来读卡片的）挪去理解产品的内部结构。
`liteBanner` 那句还额外要求用户已经知道 skill-picker 是什么、什么叫"扫一遍"——
但小红书/抖音渠道进来的人大概率没装 skill-picker。

**方向**：提示条的位置应该让给"这一刻用户正需要的下一步"（渐进式披露），
而不是产品的结构说明书；Stories 的用途应该由它自己的空态承担（见 F-8）。

#### F-8 · P1 · Stories 空态占位不产生动机

**证据**（16:39 截屏）：无任何关注时，顶部圆环区域仍占约 75px，
只有两个灰色虚线 `+` 圆环，标签 `+ Builder` / `+ 行业`。
在 **lite 变体下这两个按钮完全无响应**——`openFollowSheet()` 与 `openIndustrySheet()`
的第一行都是 `if (IS_LITE) return;`（`:1165`、`:1203`），无 toast、无提示、静默失败。
full 变体下点击会弹 sheet，列出 `Feed 内 N 条` 的 builder / 行业。

**行为机制**：空圆环是一个**无价值的仪式性占位**——它在首屏最贵的位置
（就在搜索框下方）请求一个用户此刻完全没有理由做的承诺（关注一个他没听过的外国 ID）。
自我决定论里"胜任感"要求先有一次成功体验再邀请投入；
这里投入邀请排在任何价值交付之前。lite 版的静默失败更严重：
点击无反馈是可用性伤害里最直接的一种（用户会重复点，然后判定产品坏了）。

**方向**：关注机制应该在用户已经产生偏好之后才出现（例如连续正向互动同一 owner 后），
而不是作为首屏固定家具；lite 变体不支持的入口不该渲染出来。

#### F-9 · P1 · 「我的」页面是一张负债清单

**证据**（16:50 实测截屏 `feed-me.png`，代码 `:1902-1956`）：
新用户进入「我的」看到 5 张卡，其中 4 张是空态或错误信息：

| 卡片 | 新用户看到的内容 |
|---|---|
| 我关注的 Builder | 「还没关注 Builder。在卡片点「关注」…」 |
| 我关注的行业 | 「还没关注行业。点卡片上的场景标签即可关注。」 |
| 本机收藏 | 「点赞 0 · 书签 0」 |
| 发布与后台 | 「尚未配置云端 API（ui.api_base / skillfeed.py api）」 |
| 发现站 | 「Stories = 关注动态；下方 pills = …两者不再重复。」 |

「点赞 0 · 书签 0」旁只有一个「查看收藏」按钮——**点赞过的内容没有任何入口可查**。
「尚未配置云端 API（ui.api_base / skillfeed.py api）」是把技术配置项直接摊给终端用户。

**行为机制**：身份页/个人页在这类产品里的功能是**承载沉没投入并把它转成留存**
（IKEA 效应 + 禀赋效应：我在这里攒了东西，所以这里对我更值钱）。
现在它的实际效果相反——**零状态挫败**：5 个格子 4 个空，读起来像一份待办清单，
传达的信息是"你还什么都没做"。这是把成就展示位改造成了负债提醒位。

**方向**：身份页应该展示用户**已有的**东西（哪怕只有"你今天看过 12 条 / 属于 4 个行业"），
而不是罗列他还没有的东西；技术配置状态属于运维视图。

#### F-10 · P1 · 空态是死胡同

**证据**：
- **收藏为空**（16:51 实测）：标题「还没有收藏」+ 「双击帖子点赞，或点书签收藏。可在「我的」里查看。」
  **无任何返回发现流的 CTA**；底部导航三项全部不高亮（`saved` 不匹配任何 `data-mode`，`:1984-1987`），
  用户不知道自己在哪；顶部搜索框和两条筛选条仍然渲染（筛选一个空集合）；
  文案指向「我的」——而用户正是从「我的」点进来的，形成自指循环。
  另外"双击点赞"这个手势在界面上从未被教过（只在 `feedbackToast` 里出现过一次）。
- **搜索无结果**（16:52 实测）：这个空态**设计得反而是最好的**——
  给了「在 GitHub 搜 SKILL.md（代码）」「在 GitHub 搜仓库」两个真实出口，
  加一句诚实的「不代装：在 GitHub 选中仓库后自行安装，再回 skill-picker 跑 scan」。
  唯一问题是尾部那行漏斗 JSON（见 F-4）。
- **Stories 无内容**：`openStoryViewer` 走 toast 兜底
  「暂无最新动态 · 试试换个关联或 refresh」（`:2158`）——建议用户执行一个他无法执行的动作（refresh）。

**行为机制**：空态是**峰终定律**里最容易变成"终"的时刻。
搜索空态做对了（提供替代路径，保留自主感）；收藏空态和 Stories 空态做成了终点站。

**方向**：每个空态至少一个通向"能立刻做的事"的出口；
导航高亮状态必须覆盖所有可达视图。

### 1.3 反馈机制（详见第 4 节的完整梳理）

#### F-11 · P0 · 点赞与收藏在后端是同一个信号

**证据**：`toggleLike`（`:2047-2061`）与 `toggleSave`（`:2063-2074`）**都发 `sendFeedback('useful', …)`**。
`feedback.py:10-16` 的 `VALID_ACTIONS` 里也只有一个 `useful`。
两者的差别仅在前端：点赞多一个 `burstAt(idx)` 粒子动效，收藏没有。

#### F-12 · P1 · 四个动作的即时回报只有 toast（或什么都没有）

| 动作 | 即时反馈 | 持久化 | 后续可见性 |
|---|---|---|---|
| ❤️ 点赞 | 图标填充 + 粒子爆炸 | `sf_liked` | **无任何入口可查** |
| 👎 不感兴趣 | toast「已记下…」 | **无** | 无（且承诺是假的，F-2） |
| 🔖 收藏 | 图标填充 | `sf_saved` | 「我的」→「查看收藏」 |
| 关注 | 按钮变「已关注」+ toast | `sf_follow_*` | 顶部 Stories 圆环 |

四个动作中只有「关注」有真正的下游产物（Stories），
而 Stories 内容取自同一个本地 `FEED` 数组（`builderItems` / `industryItems`），
不是真的"最新动态"——关注 `anthropics` 后圆环里出现的是 feed 里已有的那 16 条。

**行为机制**：Hook Model 的"可变奖赏"环完全缺失。
一个动作若第二次点击的边际回报为零，它的执行率会在 3–5 次内衰减到基线。
点赞尤其是纯浪费：在**没有社交可见性**（没有点赞数、没有他人可见）
也**没有个人回看入口**的产品里，点赞既不产生社交效用，也不产生私人效用，
只剩一个 0.3 秒的动效。

### 1.4 内容疲劳与信息茧房

#### F-13 · P1 · 真实内容深度是 57，不是 388

见 F-5 的统计。用户主观感知的"新东西数量"不是条目数而是**可区分单元数**。
当 20 张卡共享同一个仓库名、同一个 star 数、同一个仓库级 tagline 时，
它们在感知上是**同一条内容的 20 个变体**。

按竖向流的典型消费速率（每卡 3–8 秒），388 条可在 20–50 分钟内刷穿；
但重复感的触发远早于此——按当前排序（前 12 条里 `anthropics/skills` 出现 2 次、
`bytedance/deer-flow` 出现 3 次、`heygen-com/hyperframes` 出现 2 次），
**第 15–25 张卡就会触发"我是不是在看同一个仓库"的判断**。

`rank.py` 的 `rerank` 没有 owner/repo 配额；设计文档里的
`max_owner_per_window: 3` / `max_consecutive_scene: 2` 尚未落地。

**方向**：owner 级配额比 scene 级更紧急（scene 有 10 类，owner 有 55 个但分布极不均）；
子 skill 的呈现应该考虑"折叠为仓库卡 + 可展开"这类结构，
把 20 次重复曝光换成 1 次高质量曝光。

#### F-14 · P2 · 有终点，但终点太远、且和无限流混在一起

**证据**（`:2011-2015`）：列表末尾 sentinel 有两态——
未看完显示「下滑加载更多 · 已显 **N** / M」，看完显示
「你已看完 · 共 **M** 条（含知识库 backup）」。
`PAGE = 6`，`maybeLoadMore()` 每次 +6（`:2018-2027`）。

**评价**：「你已看完」这个设计是**对的**，方向也正确——
Zeigarnik 效应（未完成的任务持续占用认知）需要一个闭合点，
而闭合点同时是最好的复访承诺位置（"明天再来"只能在"今天结束了"之后说）。
但 M=388 时这个终点实际不可达；而"已显 6/388"的进度提示反而制造了**目标梯度反效果**——
Kivetz 的研究里进度条加速努力的前提是终点可见，1.5% 的进度条只提示"路很长"。

**这个品类适合有终点。** 抖音的无限流服务于"消费时长"这个变现目标；
skill-feed 的目标是"促成一次安装"，用户装完一个 skill 就该去用它，
继续刷反而降低转化（决策疲劳：Iyengar & Lepper 的果酱实验里 24 种选择的购买率
是 6 种的 1/10）。**无限流与产品目标是对立的。**

**方向**：把 388 条切成有节律的"每日份量"（20–30 条），
让「你已看完」在 3–5 分钟内可达，并把它作为复访承诺的锚点。

#### F-15 · P2 · 15% 探索位：比例合理，但不该标记给用户

设计稿（`docs/ranking-engine-design.md` §5.3）：每 20 槽固定 3 槽，位置 5/12/17，
其中至少 1 个给新品，探索池忽略 scene/owner 级负反馈压制。

**行为学评价**：
- **15% 合理**，甚至偏保守但在这个库存规模下是对的。参照多臂老虎机的 ε-greedy 实践，
  当候选池只有 57 个可区分单元时，过高的探索率会直接暴露"库里没东西了"。
  真正的约束不是探索率而是 F-13 的内容深度——**探索位的价值上限由内容多样性决定，不由比例决定**。
- **位置 5/12/17 里，5 太靠前**。第一屏（前 3–4 卡）承担品类识别与自我关联（F-6），
  这时插入一条画像外内容会稀释"这个产品懂我"的第一印象。
  探索的收益是长期的，代价是即时的；在首会话应该延后。
- **不要标记**。这是最重要的一条：给探索位打标签（"试试新领域""为你破圈"）
  会激活**理由化拒绝**——用户获得了一个现成的归因去跳过它（"这条是系统随便塞的"），
  探索位 CTR 会显著低于不标记。反过来，如果不标记而用户自己点开了，
  他会把这次发现归因为**自己的品味**（内在归因），这才是探索位真正想要的效果：
  扩大用户对自己兴趣边界的自我认知。
  设计稿里 `exploration_slot_ctr / overall_ctr` 目标 0.5–1.0 是合理的期望；
  标记会把它压到 0.3 以下。
- 唯一值得标记的是**事后**：用户已经打开了一条探索位内容之后，
  可以告诉他"这条不在你常看的行业里"——此时标记服务于自我认知扩展，而不是提供拒绝理由。

### 1.5 中国用户语境

#### F-16 · P1 · 抖音形态与"找工具"目标存在结构性张力

**迁移正确的部分**：
- 低决策成本的浏览姿态（不需要先想清楚要什么就能开始）——这恰好匹配
  "我不知道有什么 skill 可用"这个真实起点，比搜索框友好。
- 封面 + 一句话 + 3 条亮点的信息密度，适合快速筛选。
- 行业标签作为筛选入口，符合小红书的"逛品类"习惯。

**水土不服的部分**：
- **奖赏位置错了**。抖音的奖赏在 app 内即时兑现（看完这条就爽了），
  用户越刷越满足，平台目标与用户体验同向。skill-feed 的奖赏在 app 外
  且延迟数十分钟（装完、配好、跑一次才知道有用）。
  这导致一个反直觉的后果：**用户刷得越顺畅，转化越低**——
  流畅的浏览本身变成了目的，"再看一条"的成本比"去装一个"低太多。
  这不是文案能解决的，是形态选择的固有代价，必须靠"制造离站"的设计对冲（见第 2 节）。
- **卡片信息量与决策所需信息量不匹配**。决定装一个 skill 需要知道：
  和我的 agent 兼容吗、装了会不会和现有 skill 冲突、卸载麻烦吗。
  这三个问题卡片一个都没回答，而抖音式的卡片形态**在结构上容纳不了**它们。
- **英文内容比例**。55 个 owner 绝大多数是英文 ID，
  tagline 在中文界面下仍是英文（F-6）。小红书渠道用户对英文界面的容忍度很低。

#### F-17 · P1 · 两类来源用户被一视同仁

从小红书/抖音点进来的用户携带的是**好奇 + 低承诺**（"看看这是什么"），
主动搜索来的携带**明确任务 + 高承诺**（"我要找一个做周报的 skill"）。
当前界面对两者提供完全相同的入口：同一个 feed、同一个搜索框、同一批前 3 卡。
代码里没有任何来源分流（无 UTM 读取、无 referrer 分支、无 landing 差异）。

**行为机制**：这两类人的**首要心理任务完全不同**——
前者需要"这是什么品类 + 一个 wow 时刻"，后者需要"最短路径到答案"。
用同一套体验服务两者，结果是对前者太干（一上来就是仓库名和 star）、
对后者太绕（要在竖向流里滑找，而不是直接给答案）。
搜索框已经存在且质量不错（有短词提炼、有 GitHub 兜底），
它本可以成为高承诺用户的主路径，但它被放在了一个"逛"的界面里。

#### F-18 · P1 · 「关注 Builder」在中国开发者语境下动机极弱

对比三个已有的心智模型：

| 机制 | 用户得到什么 | 触达方式 | 互惠压力 |
|---|---|---|---|
| GitHub star | 收藏夹 + 给作者的认可 | 无推送 | 弱（但作者可见，有社交意义） |
| 公众号关注 | 内容推送 | **有主动触达** | 无 |
| 微信群 | 人际连接 + 提问渠道 | 有 | **强** |
| skill-feed 关注 | 顶部圆环里优先看到 | **无任何站外触达** | 无（Builder 不知道你关注了） |

skill-feed 的关注**三个动机源一个都不具备**：
无推送（关注了也要主动回来才看得到）、
无社交可见性（`anthropics` 永远不知道你关注了它，没有 Cialdini 的互惠也没有身份表达）、
无稀缺性。而它要求的却是**对一个陌生英文 ID 的持续性承诺**。

更根本的问题：中国开发者社区里"关注人"这个行为的载体是微信/公众号，
GitHub 上的对应行为是 star 仓库而不是 follow 人。
skill-feed 把一个在中文语境里没有对应习惯的动作放在了卡片最显眼的右上角。

**方向**：如果关注要留，它需要一个真实的下游产物（站外触达是最直接的，
但这需要微信服务号/订阅机制）；
在没有触达能力之前，"关注行业"比"关注 Builder"合理得多——
行业是用户对自己的描述（身份表达），Builder 是对他人的承诺。

### 1.6 长期习惯养成

#### F-19 · P0 · 没有任何"明天再来"的理由

穷举现有的复访触点：
- 站外触达：**零**（无邮件、无推送、无微信服务号、无 RSS）
- 站内承诺：仅 `「你已看完 · 共 388 条」`（F-14），后面没有跟"明天有新的"
- 新鲜度信号：仅页头 `更新 9月3日 16:49`（`fmtGeneratedAt()`，`:1009`），
  约 10px 灰色小字，且它显示的是**构建时间**，不是"新增了几条"
- 新内容标记：**不存在**。卡片徽标只有 `scene` / `scene_l2` / `知识库` / `线索`
  （`:1662-1667`），没有"新"标识。`feed.json` 里有 `stars_today` 字段，
  但前端 grep 无任何引用。
- 未完成状态：无跨会话记忆（`state.shown` 每次刷新归零，
  没有"上次看到第 N 条"的续读）

**行为机制**：习惯回路 `提示 → 行动 → 奖赏 → 投入` 里，**最弱的一环是「提示」，
而且弱到回路无法闭合**。行动（滑动）门槛低、奖赏（发现有用的 skill）偶发但真实、
投入（收藏/关注）有控件——但没有任何东西会在明天提醒用户这个产品存在。
习惯形成需要提示的**情境稳定性**（同一时间、同一场景重复出现），
而这个产品的唯一提示是用户自己想起来。

次弱的一环是「投入」：F-9 里投入产物不可见，F-11/F-12 里投入不产生下游价值。

**方向**：站外触达能力是这个产品长期留存的前提条件，而不是优化项。
在没有触达的情况下，唯一可行的替代是**寄生在用户已有的高频回路上**——
skill-picker 就是那个回路（用户每次要选 skill 都会打开它），
这也是第 2 节要讲的核心对策。

#### F-20 · P2 · 6 小时刷新完全不可感知

刷新会重建 `feed.json`（观察期内实测发生过一次：08:39Z → 08:49Z）。
用户侧的唯一变化是页头时间戳，和整个 feed 的顺序/内容悄悄换了一批
（16:39 首卡是 `hardikpandya/stop-slop`，16:49 重建后首卡变成 `maillab/cloud-mail`）。

**行为机制**：这是**"变化不可见"的最坏组合**——
后台确实在产生新价值，但用户既感知不到新增（没有 N 条新）、
又会因为"我上次看的那条找不到了"而损失控制感。
新鲜度必须被主动叙述才有留存价值；静默更新等于没更新。

## 2. 专章：「送去 GitHub 就失去闭环」

### 2.1 断点在哪，有多致命

成功路径的 6 环，逐环评估动机强度与摩擦：

| 环节 | 动机来源 | 摩擦 | 产品可见性 | 评估 |
|---|---|---|---|---|
| ① 看到卡片 | 好奇 / 浏览惯性 | 低 | 可见 | 通畅（但 F-6 影响第一印象） |
| ② 产生兴趣 | 亮点文案 + 自我关联 | 低 | 可见 | 可行，质量取决于文案 |
| ③ 点开 GitHub | 探索欲 | **中**（离站、换语言、新标签） | 可见（`opened_github`，但线上丢信号） | 转化的第一个悬崖 |
| ④ 真的安装 | 需求强度 | **高**（英文 README、路径、依赖、多宿主差异） | **不可见** | **主悬崖** |
| ⑤ 用起来 | 任务驱动 | 中（还得想起来用） | **不可见** | 不可见 |
| ⑥ 回来找下一个 | 上一次的成功体验 | 高（无提示，F-19） | — | 基本不发生 |

**③→④ 的断崖有多致命，可以量化地推理**：GitHub 仓库页对一个中文内容创作者而言，
是一次**语言 + 领域 + 工具链**的三重切换。
他要在英文 README 里找到安装段落，判断 `~/.claude/skills` 和 `~/.cursor/skills` 哪个是他的，
执行一条命令或手工复制目录，然后（这一点最容易被忽略）**回到他原本要干的活上**——
而他打开 skill-feed 时本来只是在闲逛。
行为经济学里这叫**意图-行动缺口（intention-action gap）**：
Gollwitzer 的研究显示，没有实施意图（具体的 when/where/how）支撑的行为意图，
落地率通常在 20–40%；而这里还要叠加语言摩擦。
更关键的是：**这个断崖发生在产品的视野之外**，
所以它既不能被测量、也不能被干预、也不能被归因。
产品甚至不知道自己在这一环损失了 60% 还是 95%。

### 2.2 失去闭环对留存与复访意味着什么

1. **没有成功体验可以强化。** 复访的第一驱动力是"上次这里帮我解决了问题"。
   产品无法知道谁成功了，也就无法在成功后立即强化（"你装的 stop-slop 已经在用了，
   要不要看看同作者的另一个"）。所有用户被当成同一类未知状态对待。
2. **产品无法给出完成感，用户就自己找不到完成感。** 峰终定律里，
   一次会话的"终"现在是"我关掉了一堆 GitHub 标签页"——
   一个典型的**未完成 + 略带负担**的结尾。这会被编码为对产品的整体印象。
3. **数据飞轮不启动。** F-3 已证信号通道断了；即使通了，
   `opened_github` 也只是**离站意图**而不是**成功**。
   把 `opened_github` 当正样本训练排序，会系统性地偏好"标题吸引人但装不上/不好用"的条目——
   这是推荐系统里典型的代理指标错位（optimizing for the proxy）。
4. **无法建立质量信誉。** 一个发现型产品的长期护城河是"这里推的东西都靠得住"。
   没有安装/使用回流，产品对"靠得住"这件事永远只有 star 数这一个失真的代理（F-5）。

### 2.3 不做安装功能，如何补上闭环

按"性价比 × 行为有效性"排序。**都是方向，不含实现。**

#### 对策 A（最高优先，且这个产品独有）· 用 skill-picker 的 scan 做安装验证器

这是整个评审里我认为最重要的一条建议。

用户装完 skill 之后，**skill-picker 的 `scan` 会在本机看到这个新目录**——
产品其实拥有一个完整的、零成本的、不依赖用户自我报告的安装验证通道，
只是这两个产品目前没有握手。
所需的只是一个"从 feed 送出去的 full_name" 与 "本机 catalog 里新出现的 skill" 之间的对账。

行为学上这条对策同时解决四件事：
- **成功强化**：用户下次打开 skill-picker（一个高频入口）时，
  产品第一次有能力说"你从 feed 装的 X 已经在这台机器上了"——
  这是操作性条件反射里迟到但真实的强化物，且落在**用户会主动回来的场景**里（F-19 的提示缺口）。
- **完成感 / Zeigarnik 闭合**：把"我打开了一个 GitHub 标签页"这个未完成状态，
  在下一次会话里显式闭合。
- **真正的正样本**：`installed` 是比 `opened_github` 高一个量级的信号，
  能修正 2.2 第 3 点的代理指标错位。
- **两产品的联合价值**：skill-feed 单独存在时是个内容站，
  和 skill-picker 对账之后它变成"本机能力管理系统的入口"，
  这才是它相对于任何 awesome-list 的真实差异化。

需要注意的行为学风险：这个对账必须**只在用户回访时呈现为正向确认**，
绝不能变成"你打开了 8 个 GitHub 但只装了 1 个"的问责式统计——
后者会激活防御性回避，用户会开始避免点开 GitHub。

#### 对策 B · 用实施意图（implementation intention）加固离站前的一瞬

用户点「打开 GitHub」的那一刻是他动机的最高点，也是产品最后一次能说话的机会。
Gollwitzer 的实施意图研究表明，把模糊意图转成具体的 when/where/how
可以把落地率提升近一倍，而成本只是一句话。
方向：在离站的瞬间（而不是提前）交付"你到了那边要做的第一件事是什么"，
以及一个**可以带走的东西**（比 README 更短、更确定的落地路径）。
关键行为约束：这句话必须在离站**之后**才有意义（用户已经在 GitHub 页面上），
所以承载它的不应该是一个会被立刻关掉的弹窗。

#### 对策 C · 用回流检测把"离站"变成一次对话

用户从 GitHub 标签页切回来的那一刻（页面重新可见），
是唯一一个**产品确知用户刚刚经历了什么**的时刻。
此刻问一个二元问题（装上了 / 没装成）的心理成本极低，
而回答本身构成一次微承诺（Cialdini 的一致性原则：
回答"装上了"的人后续更可能真的去用）。
行为学要点：
- 必须是**二元或三元的单击**，不能是表单；
- "没装成"必须比"装上了"更容易点，且导向帮助而不是导向沉默——
  否则这个控件会变成 F-2 那种谎言按钮的另一个版本；
- 采样率要低（不是每次都问），否则从"关心"退化为"骚扰"。

#### 对策 D · 把"打开 GitHub"的单一 CTA 拆成两个不同承诺层级的动作

现在卡片只有一个不可逆的高承诺动作（离站）。
中间缺一档"我有兴趣但现在不弄"的动作——收藏本可以是它，
但它现在没有下游（F-12）。
方向：让"稍后处理"成为一个**有下游产物的一等动作**
（承诺装置：用户为未来的自己留下一个明确的待办，而不是往黑洞里丢一个书签），
这样高承诺用户走 GitHub、低承诺用户留下可回收的意图，两条路都不浪费。

#### 对策 E · 对失败保持诚实，把它变成信任资产而不是隐藏它

安装失败是常态而不是异常。当前搜索空态那句
「不代装：在 GitHub 选中仓库后自行安装」的诚实语气**是这个产品最好的文案**，
它在管理预期（预期管理是满意度公式里最便宜的一项）。
方向：把这种诚实延伸到安装环节——
承认"有些 skill 你装不上，这不是你的问题"，
并让"装不上"这件事有地方可说。
行为学依据：服务失败研究里，被妥善承认的失败带来的信任高于从未失败
（service recovery paradox）；而被沉默处理的失败是流失的第一原因。

## 3. 专章：强制登录的位置与呈现

### 3.1 当前实际状态（重要修正）

**代码里不存在微信登录。** `server/auth.py` 实现的是 GitHub OAuth（`scope=read:user`）
+ HMAC 签名 cookie + 一个 `/auth/dev-login` 后门。

而现有的登录墙位置**已经是三个方案里最优的那个**：

| 路由 | 是否要登录 | 出处 |
|---|---|---|
| `GET /` 首页 | **否** | `server/app.py:66` |
| `GET /api/feed` | **否** | `:151` |
| `GET /publish` 页面 | 否 | `:71` |
| `POST /api/posts` 发布 | **是** | `:195` |
| `POST /api/posts/{id}/react` | **是** | `:237` |
| `GET /api/posts/me` | **是** | `:230` |

也就是说：**浏览完全免登录，只有写操作要登录**。
「第一版强制登录」的计划是从这个状态**往回退**。

### 3.2 三个方案的行为学权衡

#### 方案一 · 进站即墙（"第一版强制登录"）

| | |
|---|---|
| 转化影响 | 最差。用户在**零价值感知**的状态下被要求付出成本 |
| 行为机制 | 交易效用为负：付出（授权、暴露身份）先于收益（还不知道这里有什么）。<br>损失厌恶让"未知收益"的估值被系统性低估，而"授权微信"的成本被高估 |
| 中国语境的特殊代价 | 从小红书/抖音跳转过来的用户处在**极低承诺状态**（他只是好奇点了一下），<br>而微信授权在中文用户心里是一个"要不要跟这个 app 建立关系"的判断，<br>门槛远高于填邮箱。这两者的落差是最大的 |
| 什么时候可接受 | 只有当产品价值已经通过**站外**充分传达（比如公众号长文导流、<br>用户是带着明确任务来的）。skill-feed 目前不具备这个条件 |
| 附带损失 | 失去全部匿名浏览数据——恰恰是冷启动期最需要的那部分数据 |

**结论：不建议。** 在这个产品当前的认知度和内容深度（F-13）下，
进站墙会把首会话流失从"某个未知比例"直接推到接近全损。

#### 方案二 · 价值兑现点设墙（gate-on-value）

在用户已经获得价值、并且**自己想要保存这个价值**的那一刻要求登录。
候选时刻：收藏第 N 条时、想要跨设备同步时、想要发布自己的 skill 时、
想要接收"你关注的 Builder 有更新"时。

| | |
|---|---|
| 转化影响 | 最好。付出与收益在同一个瞬间对齐，交易效用为正 |
| 行为机制 | ① 互惠原则（先给再要）；② 沉没投入——已经收藏了 5 条的人不愿放弃，<br>登录成了"保护已有资产"而不是"获取未知资产"，从收益框架切到损失框架；<br>③ 一致性——他已经用行为表达了"我在意这些内容" |
| 代价 | 需要维护匿名态和登录态两套状态，以及一次数据迁移 |
| 关键设计约束 | 墙上的理由必须是**用户此刻的目标**（"登录后这 5 条收藏在你手机上也能看到"），<br>不能是产品的目标（"登录以继续使用"）。<br>前者是帮他达成他的意图，后者是收过路费 |

**结论：推荐。** 而且这正是现在的代码状态（react 要登录、浏览不要），
只需要把"墙的呈现方式"从 401 错误改成一次有理由的邀请。

#### 方案三 · 匿名身份先行，登录仅用于跨端迁移

给每个浏览器一个匿名 device 身份，所有偏好、收藏、关注先存在匿名身份上
（这也正是排序引擎设计稿里 `device` 画像的假设），
登录只在用户想换设备/怕丢的时候出现。

| | |
|---|---|
| 转化影响 | 与方案二相当，长期数据质量更好（匿名期的行为数据也被保留和使用） |
| 行为机制 | 禀赋效应最大化：用户在完全无摩擦的情况下积累了一整套"我的东西"，<br>登录的动机从"为了用功能"变成"为了不丢"。<br>而且它让个性化在**第一次会话内**就能生效——这是方案一二都做不到的 |
| 代价 | 最高：匿名 ID 生命周期、清缓存丢数据的预期管理、并档逻辑（设计稿 §10 已考虑） |
| 备案/合规视角 | 匿名 device 画像不涉及个人信息收集，在备案未完成期间反而更安全 |

**结论：这是理想终态**，也和排序引擎的 device 画像设计天然吻合。

### 3.3 我的建议

**第一版不要强制登录。** 保持现有的"浏览免登录 / 写操作登录"，
把工作放在两件事上：一是把 401 变成一次带理由的邀请（方案二的呈现层），
二是把匿名 device 身份立起来（方案三的地基，排序引擎也需要它）。

理由不只是转化：**强制登录会让 F-3 变得不可修复**。
现在反馈信号已经断了，如果再加一道登录墙，匿名用户连"我看了什么、跳过了什么"
都不会产生数据，冷启动期的排序引擎将没有任何东西可学。
在内容只有 57 个可区分单元（F-13）的阶段，把用户挡在门外换取账号，
是用最稀缺的资源（首会话注意力）去买最不缺的东西（一个尚无用处的账号体系）。

## 4. 专章：四个反馈动作的语义梳理

### 4.1 从用户视角看，它们现在各自意味着什么

| 控件 | 用户以为它是什么 | 系统实际做了什么 | 落差 |
|---|---|---|---|
| ❤️ 点赞 | 表达喜欢 / 攒一个"喜欢过的" | `sf_liked` + 发 `useful` + 粒子动效 | **无处可查**，纯情绪表达且无接收方 |
| 👎 不感兴趣 | 让它别再推这类 | 发 `bad` + toast，**当前会话零效果** | 承诺 vs 现实的完全落差（F-2） |
| 🔖 收藏 | 存起来待会儿看 | `sf_saved` + **也发 `useful`** | 与点赞在后端同一信号（F-11） |
| 关注 | 订阅这个人的更新 | `sf_follow_builders` + Stories 优先展示 | 「更新」其实是 feed 内已有的旧条目 |

### 4.2 语义重叠与缺失

**重叠 1（严重）：点赞 vs 收藏。**
后端完全等价（都发 `useful`），前端唯一差别是一个有动效、一个有列表。
从用户视角，"我喜欢这个" 和 "我想留着这个" 在**一个没有社交关系的工具型产品里
本来就难以区分**——小红书里点赞是给作者的反馈（有接收方）、收藏是给自己的
（有归档场景），两者靠"社交/私人"这条线分开。
skill-feed 既没有作者能收到反馈，也没有归档场景（F-9），
所以这条线不成立，两个控件塌缩成一个。

**重叠 2（中等）：收藏 vs 关注。**
两者都是"我以后还想看到相关的"，区别只在粒度（一条 vs 一个人）。
但因为收藏没有下游、关注的下游又是假的（Stories 里是旧条目），
用户无法从结果反推区别。

**缺失 1（最严重）：没有"我装了"。**
这是这个产品**唯一真正重要的动作**，也是唯一能表达"我真的接受了这个推荐"的信号。
它现在不存在（`VALID_ACTIONS` 里最接近的是 `opened_github`，
但那只是离站意图，见 2.2 第 3 点）。

**缺失 2：没有"稍后处理"这一档承诺。**
现在只有"离站（高承诺，不可逆）"和"划过（零承诺）"两极，
中间缺一个可回收的意图容器（对策 D）。

**缺失 3：负反馈没有作用域。**
`bad` 一个动作同时被 `rank.py` 解释为 scene 级、l2 级、repo 级三重惩罚
（`:199-204`，`scene_neg` 和 `repo_neg` 同时累加）。
用户点"不感兴趣"时想表达的可能是"这条不行"、"这个作者刷屏"、
"这整个行业与我无关"——三者的杀伤半径差 100 倍。
在 `engineering` 占 34% 库存的情况下（设计稿 §4.1 也点到了这一点），
一次误点会砍掉三分之一内容。
**用户没有能力选择作用域，而系统替他选了最宽的那个。**

**未暴露的动作：** `VALID_ACTIONS` 里的 `wrong_scene` 和 `skip` 在前端没有任何入口
（grep 零命中）。`wrong_scene` 其实对应一个真实且高频的用户感受
（"这卡的分类是错的"，比如 `maillab/cloud-mail` 被标成「内容创作/知识库」），
但用户无法表达它，只能用 `bad` 代替——于是一个分类错误被记录成了内容质量差评，
进一步污染信号。

### 4.3 我认为正确的动作集

**设计原则**：每个动作必须回答三个问题——
① 用户意图上唯一（不与其他动作重叠）；
② 有用户**当场可见**的后果；
③ 对系统是一个**语义明确**的信号（不与其他动作共用 action 值）。

按这个标准，我认为动作集应该是：

| 动作 | 用户意图 | 必须的当场后果 | 系统语义 |
|---|---|---|---|
| **收下 / 待办**（替代点赞+收藏） | "我要用这个，但不是现在" | 计数可见 + 有地方能回去看 | 强正向 + 明确的意图信号 |
| **打开 GitHub** | "我现在就去弄" | 离站 + 回流时可对话（对策 C） | 离站意图（**不等于成功**） |
| **装上了**（新增，可由 skill-picker 对账自动产生，见对策 A） | "我真的接受了这个推荐" | 完成确认 + 闭合 | **唯一的真实正样本** |
| **不感兴趣 · 带作用域**（这条 / 这个作者 / 这个行业） | 三种完全不同的意图 | 当前列表**立刻**变化 + 可撤销 | 三个不同强度和半衰期的负信号 |
| **分类不对**（暴露已存在的 `wrong_scene`） | "推荐逻辑理解错我了" | 承认 + 不影响该条的质量评价 | 分类纠错，**与质量差评分开** |

**明确建议去掉点赞。** 在没有社交可见性、没有点赞数展示、
没有个人回看入口的产品里，它不产生任何一方的效用，
只是在挤占卡片上最宝贵的操作位，并且和收藏抢同一个用户意图。
"喜欢"是消费型产品的动作；"收下"是生产型产品的动作。

**关注的处置**：在没有站外触达能力之前（F-18），
建议把它从"关注 Builder"降格为"关注行业"——
行业是用户对自己的身份描述（自我表达是内在动机），
Builder 是对陌生人的持续承诺（需要外部激励，而外部激励不存在）。

## 5. 专章：这个产品最可能死在哪一环

### 5.1 我的判断

**不是死在获客，也不是死在内容量，是死在③→④ 的不可见断崖上——
而且是以"看起来一切正常"的方式死的。**

具体的死法（按发生顺序）：

1. 小红书/抖音的内容能带来第一波流量。竖向流的形态在中文用户里有天然亲和力，
   `opened_github` 的比例可能看起来还不错——因为"点开看看"的成本很低。
2. 但④ 安装环节的转化在产品视野之外（2.1），
   没人知道它是 5% 还是 30%。产品会用 `opened_github` 当作成功指标继续优化，
   于是排序开始系统性偏好"标题吸引人"而不是"真的能装上、能用"（代理指标错位）。
3. 用户第一次会话结束时手里只有几个关掉的 GitHub 标签页，
   没有一次成功体验（2.2 第 1、2 点）。
4. 没有任何东西提醒他明天再来（F-19）。他不会回来。
   而这件事在数据上表现为"次日留存低"，
   会被误诊为"内容不够多"——于是团队去扩内容（212 → 388 → 500+），
   但真实瓶颈是可区分单元只有 57 个（F-13），扩内容不解决问题。
5. 同时，因为反馈通道断了（F-3），个性化永远不会启动，
   产品无法通过"越用越懂我"挽回任何东西。

**这个死法最危险的地方在于它没有明显的失败信号。**
不会有崩溃、不会有差评、不会有明确的流失点——
只会是一条缓慢下滑的曲线和一堆看起来合理但没用的优化。

第二可能的死法（可能性略低但更快）：**信任在第一次会话内崩塌。**
触发链是 F-5 → F-2：用户先发现"这 20 张卡的 star 都是 17 万"，
再发现"我按了不感兴趣它还在推"，
然后合并成一个判断——"这个站是机器批量抓的，不是有人在选"。
对一个以"策展"为价值主张的产品，这是最致命的判定。
（讽刺的是，这个产品的门禁体系 `gates.py` 是真的在做质量筛选，
只是所有对外呈现都在暗示相反的事。）

### 5.2 最小成本的验证方法

按"能否伪证核心假设 / 成本"排序。都不需要写产品功能。

**验证 1 · ④ 安装环节的真实转化率（最高优先，因为它决定产品是否值得继续）**

现在完全不知道这个数字，而它决定一切。
最小成本做法：拿 10–20 个真实目标用户（小红书渠道来的内容创作者，不是开发者），
让他们在自己的机器上从 feed 出发装一个 skill，全程旁观，
只记两件事——**多少人装成了**、**没装成的人卡在哪一步**。
- 如果转化 > 30%：断崖没那么致命，重点应该放在闭环回收（对策 A/C）和复访（F-19）。
- 如果转化 < 10%：**产品的核心假设（"送去 GitHub 就够了"）被伪证**，
  必须重新考虑要不要碰安装这件事，或者把目标用户改成"已经会装的人"。

这个测试一天能做完，成本几乎为零，但它是唯一能区分"要优化"和"要转向"的实验。

**验证 2 · 反馈按钮的可信度（一次会话就能观察）**

让 5 个用户各刷 20 张卡，不给任何提示。观察两件事：
**他们主动点了几次反馈按钮**、以及**第一次点完之后还点不点第二次**。
如果第二次点击率显著低于第一次，F-2 的期望违背假设得到证实。
更直接的做法：在他们点完"不感兴趣"之后，问一句"你觉得刚才发生了什么"。

**验证 3 · 社会证明失真是否被察觉（10 分钟）**

让用户连续刷过同一仓库的 5 张卡（当前排序下很容易触发），
不提示任何东西，事后问"你觉得这些卡片是人工挑的还是机器抓的"。
如果多数人回答"机器抓的"，F-5 的信任崩塌路径就是真的。

**验证 4 · 复访理由的存在性（零成本的思想实验，但需要诚实回答）**

对着现在的界面回答一个问题：**如果我是用户，什么事情会让我明天想起这个网站？**
如果穷举完 F-19 那个列表之后答案是"没有"，
那么在补上任何一个触点之前，所有别的优化都只是在优化单次会话的体验，
而不是在做产品。

**验证 5 · 内容深度的感知上限（半小时）**

让用户一直刷到他自己说"没意思了"，记录他停在第几张。
如果这个数字明显小于 388（我预计在 15–30 之间，理由见 F-13），
那么"扩内容到 500+"这条路线的收益需要重新评估——
真正要修的是 owner 配额和子 skill 的折叠呈现，不是条目总数。
