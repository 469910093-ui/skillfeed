# 品牌令牌：取值依据与禁用清单

这份是**活文档**，描述当前生效的品牌色板与字体，同时是品牌合规的规范来源。
改动这些值之前请先读完「为什么中性灰不动」那一节，那是最容易好心改错的地方。

## 当前令牌

`--accent` 的 HSV 饱和度是 0.97，明度压在 0.47。选深青绿是为了同时离几样东西足够远：
消费社交类 App 常用的暖色→洋红渐变、各类 AI 产品的紫、以及微信绿 `#07C160`（亮而高饱和）。
区分靠的是**色相 + 明度**，不是靠压饱和度——早先那版把饱和度压到 0.74 换来的只是显脏，
拉满饱和后色相仍在 165°，和上面几样在色相环上的距离一点没变，AA 也还在（5.48 / 5.25）。

`Outfit` 采用 SIL Open Font License 1.1，允许商用与网页嵌入；改字体时请一并确认新字体的
授权允许 web embedding，并把结论记在这里。

对比度不是估的，是按 WCAG 2.x 相对亮度实算的；`--muted` / `--link` / `--like-ink` 这三个值
是在各自色相与饱和度上**逐档降明度搜出来的「刚好过 AA 的最亮值」**，所以往亮的方向动一档就会掉出 AA：

- `--muted` `#737373` → 再亮一档 `#747474` 掉到 4.48
- `--like-ink` `#d6344c` → 再亮一档 `#d7344c` 掉到 4.49

`tests/test_feed_dashboard.py::TestContrastTokens` 会用真实数值复算，底色从 `--card` / `--bg`
令牌里读而不是写死，所以换底色也逃不掉这道门。

## 禁用清单：不得使用的第三方品牌标识

品牌要素必须是我们自己的。下面这些取值属于第三方，页面外壳里不得出现
（`<style>` + head + 静态 markup），由 `TestBrandIdentityIsOurOwn` 把门。

| 禁用 | 是什么 |
|---|---|
| `Billabong` | Instagram 字标所用字体 |
| `#f09433` `#e6683c` `#dc2743` `#cc2366` `#bc1888` | Instagram 的 5 段暖色→洋红品牌渐变 |
| `#ed4956` | Instagram 的点赞红 |
| `#00376b` | Instagram 的链接蓝 |
| 外观描述里出现第三方产品名 | 自称某产品同款是「意图」的书面证据，在纠纷里比色值更难解释 |

保留具体归属是有意的：一份只写「禁用 `#ed4956`」而不说为什么的规矩，下次就会有人
换个相邻值绕过去。这是合规控制清单，不是历史记录。

### 这道门曾经漏过三种写法

清单一开始只做「hex 字符串比对」。实测下来它漏掉了三类东西，都已补上：

1. **十进制写法。** `.badge.kb`、`.badge.local.drift`、`hintFlash` 三处写的是
   `rgba(237,73,86, …)`，而 `237,73,86` 就是 `#ed4956`。同一个颜色换个记法，
   只比字符串的断言一路是绿的。现在带 alpha 的红必须走 `--like-rgb` 令牌，
   `test_banned_values_are_also_caught_when_written_as_rgb` 会把 `rgb()`/`rgba()`
   折算回 hex 再比一遍。
2. **微调一档。** 把 `#ed4956` 写成 `#ed4957` 就能过清单——文档早写了这是预期的
   失效模式，但没有任何东西在挡。现在 `MIN_DISTANCE = 40` 按 RGB 欧氏距离拦，
   用的是 RGB 而不是 CIEDE2000：这道门要挡的是「照着清单微调」，不是判断人眼能否
   分辨，RGB 够用且不引依赖。
   门自己的灵敏度也有测试（`test_the_distance_gate_is_actually_sensitive`）：
   把阈值调到 0 时上一条断言照样是绿的（没有违规色时，「门在」和「门被拆了」
   的结果都是空列表），所以那条测试往同一条代码路径里塞一个距禁用值 5 的合成色，
   必须被报出来。
3. **整体结构而非单点取值。** `.sv-slide`（全屏 story 背景的 CSS 兜底）原来是
   `#7c3aed → #db2777 → #f59e0b`，紫→洋红→橙三段暖色扫掠。逐段 hex 都不是精确
   匹配（最近的 `#db2777` 距 `#cc2366` 有 23），但「竖屏全屏 story + 暖色洋红扫掠
   背景」这个组合正是要避开的整体印象。已改成 accent 单一色族。

**豁免清单现在是空的**，`GRANDFATHERED = frozenset()`，刻意留空而不是删掉。

它曾经装着 `--like` / `--like-ink`：上一版的 `#e0364f` / `#d6344c` 距禁用的
`#ed4956` 只有 20 / 17，按上面第 2 条的标准就是「相邻值」，当时按品牌决策挂账。
后来两者都挪到纯红一路（`#b91c1c` / `#991b1b`），距离升到 54 / 79，豁免就没了存在
理由。留着这个空集合是为了让「又要加豁免」这件事必须显式写进代码被人看见——
每加一个近似色就顺手加一条豁免，清单会被蚕食成一张白名单。

挪红的代价记一句：更亮的红做不到。往洋红方向走，40 以上余量的取值不存在——
在色相 0-15°、饱和 0.70-0.90、明度 0.38-0.46 的范围里扫过 209 个候选，
所有距禁用值 ≥55 的都落在填充对比度 6.15 以上。所以「已赞」的心比原来沉，
这是合规换来的，不是没调好。

### 断言范围

范围分两层，因为两类东西的判定标准不同。

**内容数据剔掉，外观常量必须扫。** 剔掉的只有注入的三条数据声明
（`const FEED / SCENES / SCENES_L2 = ...`）。feed 里正当存在提到第三方
产品的条目（`instagram-curator`、"TikTok and Instagram carousel" 之类的第三方
skill），**指名提及真实产品是正当使用**，不构成侵权，也不该被清洗——那样会砸坏内容。
对整页 HTML 做字符串断言会在空 feed 下是绿的、一有真实内容就炸，属于最难查的那种假绿，
所以测试里专门放了一条这样的夹具条目来证明不会误报。

**颜色取值另外还剔掉注释，第三方名字不剔。** 判定标准不同：**颜色按渲不渲染判**，
注释里的值没有外观，写在那儿通常正是为了记录「这个值被否掉了」——
`--like` 上面那条就记着它为什么不能往洋红方向走。把它算成违规等于逼后人删掉决策记录。
而**第三方名字按出不出现判**，仍然扫含注释的全外壳：自称某产品同款是意图的书面证据，
在纠纷里比色值本身更难解释。剪注释的正则本身有测试兜
（`test_the_comment_stripper_does_not_eat_live_css`）：`/\*.*?\*/` 配 DOTALL 在含
`/*` 的字符串上会吃掉整段，那样下面几条断言就是在空串上空过。
JS 的行注释按 `(?<![:/])//` 剔，前瞻是为了不把 `https://` 当成注释起点。

这条界线是**修出来的，不是设计出来的**。原来整个 `<script>` 都被剔掉，理由写的是
「script 里是内容数据」——那句话对**数据**成立，对**外观常量**不成立，而当时没有
区分。代价是一整类东西在门外待了很久：`PALETTES`，八组三段渐变，驱动头像字母底、
story 环面、行业面板头像，以及**全屏 story 背景**。实测其中四组贴着禁用值：
第 1 组 `#ff6a3d → #c32bad → #7028e4`（橙→洋红→紫，两段分别距禁用值 25 和 42）、
第 3 组（距 22 / 26）、第 5 组（洋红→橙→黄）、第 8 组 `#fc466b`（距 26）。
「清掉 Instagram style」那一轮只覆盖了 CSS 外壳，这批全活了下来。

现在 `PALETTES` 已被十套 scene 板取代（见下一节），范围也改成「剔数据、扫代码」，
两件事一起做的：只换调色板会留着同一个敞口等下一批颜色掉进去。
`test_the_script_scan_sees_the_palettes` 反向盯着这件事——它直接要求调色板的色值
必须出现在被扫文本里，同时要求注入的内容数据必须不在。把范围退回只扫 CSS，
它会先红。

`--ring` 这条渐变的曝光面值得单独提一句：它同时用在字标区和**每张卡片的头像环**上，
是全页复现次数最多的品牌要素，所以它必须留在 `--accent` 单一色族内
（`test_ring_gradient_is_one_hue_family` 把色相跨度锁在 30° 内）。

这条约束和「渐变要跳」是直接冲突的：三段都在一个色族里，就只能靠饱和度和明度拉开差异，
拉不出跨色相渐变那种张力。这是有意选的——渐变本身就是最容易被认成第三方品牌的那个要素。

另有一件事必须一起改：环的作用是标记「有新内容」，靠的是彩环 vs 灰环。这是**纯颜色区分**，
按 WCAG 1.4.11 渐变每一段都得对灰环有 3:1。原来的灰环 `#dbdbdb` 太深，任何足够亮的绿都过不了，
所以灰环提到 `#e8e8e8`（也就是引导环原来的值），引导环再让一档到 `#f0f0f0` 保住视觉层级。
`TestRingStillSignalsNewContent` 会逐段复算。
顺带说明：这只解决了看得见的对比，**屏幕阅读器仍然完全不知道哪个头像有新内容**，
环上没有任何文本或 `aria` 标记——那是一个还没修的可访问性缺口，不要把这段当成已经修完。
字标用 `Outfit` 800 实心字，`.logo` 上不设 `background-clip: text`——
「手写体字标 + 渐变填充」这个组合的辨识度来自组合本身，两样都不用比只换一样更稳。

## 分类色：十套 scene 板

取代了原来八组按名字哈希的随机渐变。换掉是**两个问题一次解决**，两条动机都得记住，
不然后人只会看到「颜色变了」：

1. **合规。** 旧那八组里有三组是暖色的紫→洋红→橙扇推，和被禁的那家的商标外观结构
   相似；而它们全写在 `<script>` 里，当时的门看不见（见上一节）。
2. **信息着色。** 旧颜色按 repo 名哈希，同一分类的卡每张一个色。颜色对读者恒等于
   噪声——页面被反馈「丑」的真因不是取值难看，是满屏灰字加约 2% 面积的强调色，
   信息全没上色。现在颜色键入 `scene`，蓝=工程开发、紫=Agent 工具链，扫一眼能筛。

| scene | 色相 | 深 `pal[0]` | 中 `pal[1]` | 浅 `pal[2]` |
|---|---|---|---|---|
| `quality` Bug与质量 | 17° | `#7c2d12` | `#c2410c` | `#ea580c` |
| `biz-vertical` 业务垂直 | 22° | `#5c2508` | `#78350f` | `#9a4a16` |
| `content` 内容创作 | 35° | `#854d0e` | `#a16207` | `#ca8a04` |
| `research` 研究与知识 | 86° | `#3f6212` | `#4d7c0f` | `#65a30d` |
| `collab` 协作办公 | 142° | `#166534` | `#15803d` | `#16a34a` |
| `engineering` 工程开发 | 201° | `#075985` | `#0369a1` | `#0284c7` |
| `other` 其他 | 215° | `#334155` | `#475569` | `#64748b` |
| `data-review` 数据与复盘 | 243° | `#4338ca` | `#4f46e5` | `#6366f1` |
| `agent-tooling` Agent工具链 | 263° | `#4c1d95` | `#5b21b6` | `#6d28d9` |
| `design` 设计与视觉 | 271° | `#7e22ce` | `#9333ea` | `#a855f7` |

`pal[1]` 是头像与分类徽章的纯色底，十套都过了白字 4.5:1（最低 `content` 的 4.92）。
渐变只在同色族内从深走到浅——和 `--ring` 同一条理由：跨色相扇推是最容易被认成
第三方品牌的那个要素。

### 为什么色相是这么分的

可用色相被两头挤掉：150-180° 留给 `--accent`（那一段的含义是「被强调」，分类色占
进去就是语义串台），310-360° 是禁用的洋红/红。剩下约 280° 要分十类。

硬凑十个等距色相会把某几类推进禁用邻域，所以按**占比**分配：占比最大的三类
（工程 24%、Agent 18%、设计 17%）拿最拉得开的色相；最小的两类（其他 4%、
业务垂直 1%）走中性或低饱和，不占色相预算。

`agent-tooling` 与 `design` 色相只差 8°，靠**明度档位**错开：agent 取 violet-800、
design 取 purple-600，肉眼是「深紫 vs 亮紫」。`engineering` 与 `content` 同理。
这条路是试出来的：把 `engineering` 往深处调会撞上禁用的链接蓝 `#00376b`，
往浅处调又掉出对比度，190-215° 这段确实挤。

现在离禁用值最近的自有色是 `engineering` 的 `#075985`，距链接蓝 43，刚好在门内。

### 四道门，以及它们各自的灵敏度测试

`TestSceneColoursCarryInformation` 守四件事，每一件都配一个「已知坏样本」探针：

| 门 | 拦什么 | 阈值 |
|---|---|---|
| 覆盖率 | 加了一级场景但忘了配色（那一类会静默落进 `other` 的灰蓝） | 清单从 `scene.py` 取，不在测试里抄 |
| 单色族 | 某套板被改成跨色相扇推 | 色相跨度 ≤ 30° |
| 互相可分 | 两类的 `pal[1]` 撞色，颜色不再能区分分类 | RGB 距离 ≥ 40 |
| accent 保护带 | 分类色占进强调色的色相段 | 150-180° 禁入 |

灵敏度探针是必需品而不是锦上添花：这四道门里有三道，最初都放过了「把阈值放宽到
等于关掉」这种变异——因为真实取值本来合规，放宽阈值当然还是绿。
`test_every_threshold_gate_is_actually_sensitive` 把已知坏样本喂进**同一个判定函数**，
所以判定逻辑和探针不可能各自漂移。

另有 `test_the_badge_colour_is_derived_from_the_scene_not_the_name`：徽章的颜色必须
由 `paletteForScene(sceneId)` 来，退回按名字哈希会让这次改动的全部意义消失，而其他
断言都察觉不到（变量名没变，变的是它从哪来）。

### 颜色不是唯一的信息载体

分类徽章里必须同时有分类名的文本（WCAG 1.4.1）。颜色是给视觉用户的加速器，不是载体
本身——去掉文字只留色块，读屏用户和色觉障碍用户就完全拿不到分类了。
`test_colour_is_never_the_only_thing_saying_which_scene_it_is` 盯着这件事。

发布者头像仍按名字哈希，池子换成上面这十套。头像色是身份指纹不是分类，读者本来不会
去解读它；而池子统一之后，需要豁免的颜色一个都不剩。

## 可以放心用的通用惯例

这些是功能性的行业通用交互，不构成任何人的品牌识别，无需回避：

单列窄壳（`--phone: 448px`）、卡片流、圆形头像横条、双击点赞、红心=已赞、书签=收藏、
底部 tab 导航、无限滚动加载。

## 功能命名：用描述功能的词，不借用别家的产品叫法

顶部那排圆形头像在界面上叫**动态圆环**（英文 `updates ring`）。它之前叫
「Stories」——那是某几家消费社交 App 用开的叫法，交互本身是通用的，但**名字**没必要蹭。
面向用户的文案、公开文档、CLI 帮助里都用「动态圆环」。

代码里的标识符是另一回事，**刻意没改**：CSS 类 `.story` / `.stories`、DOM id
`storiesWrap`、函数名 `renderStories` / `openStoryViewer`、i18n 键名 `storiesHint`、
localStorage 键 `sf_stories_hint_dismissed`。理由有两条，各自都足够：

1. 标识符不可见，不构成对外的品牌表述，没有风险可言。
2. `sf_stories_hint_dismissed` 一改名，所有老用户已经关掉的提示会重新弹出来——
   为了一个看不见的字符串去打扰用户，不划算。

所以「改名」这件事的边界是：**字符串字面量里面向用户的部分改，标识符不动**。

## 为什么中性灰刻意不动

`--bg: #fafafa`、`--ink: #262626`、`--line: #dbdbdb` 这几个中性值**保持不变**，理由是：

1. 浅灰不构成任何人的品牌识别。几千个站点在用同一批中性值，没人拥有它们。
2. 挪到 `#f5f6f7` 这种量级的位移（RGB 曼哈顿距离 8~18）肉眼看不出差别，
   法律上也不减少任何风险，只会让上面那张表里的实测比值全部作废、并在 diff 里制造噪音。
   这是「看着像修了、其实什么都没变」的改动。
3. 要换就得换出可感知的差别（比如整体转冷或转暖一档），那是一个独立的品牌决定，
   需要连带重算所有文本令牌的对比度，不该和品牌合规混在一起做。

## 已知的遗留问题

- `fonts.googleapis.com` 在国内不可达，Outfit 会回退到 `PingFang SC`。字标是 Outfit 800，
