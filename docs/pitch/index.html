定位

一边是岗位上的真问题，一边是散落在 GitHub 上的 Skill。

刷一刷

skillfeeder.cn 线上站。搜索意图，下滑卡片，主按钮只有「打开 GitHub」。

两端是谁

一边要被解决，一边要被看见。

C 端 · 需求

需要被解决的用户

刚装上 Cursor / Claude Code 的知识工作者、创作者、独立开发者。他们要的不是再多一个仓库，是「这件事有没有现成 Skill」。

B 端 · 供给

需要宣发的开发者

做出了 Skill / MCP 的 Builder。仓库在 GitHub，用户在小红书和编辑器里。他们缺的是被看见、被理解、被关注的入口。

C 端问题

用户不是缺仓库，是不知道怎么选、缺哪些

  • 找不到Skill 散在 GitHub、HelloGitHub、小红书和各知识库，不会写搜索式。
  • 选不准星星多不等于能用；awesome 列表太长，当下意图对不上。
  • 看不懂英文 README 太长，三秒里答不出「解决什么、适不适合我」。
  • 不会用收藏了三十个，岗位上的一件事还是没做成。

C 端解法

先了解能解决什么问题，
再决定用不用

  • 发现竖滑卡片，3 秒看清解决 / 亮点 / 适合谁
  • 对准意图搜索 + 主题分类 + 关注行业
  • 行动主按钮只有「打开 GitHub」，自己装，不代装
  • 做成本机用 skill-picker；岗位事用场景包带练

B 端问题

开发者不是缺作品，是缺被看见。

  • 没入口做好了只能等 GitHub 搜索，或求人转帖。没有面向使用者的货架。
  • 没翻译仓库说明写给同行，C 端看不懂「这能解决我什么问题」。
  • 隔着河中文热议在小红书，仓在 GitHub，两边对不上号。
  • 没关系没有人关注 Builder，出了新版本也喂不到老用户嘴里。

B 端解法

给他一条通往使用者的路。

  • 上架登录后贴 GitHub 链接，过审进入混排 Feed
  • 被读懂卡片替他把仓译成「解决什么、有何亮点」
  • 被关注发布者主页 + Builder 环，更新喂到关注者
  • 被核验小红书热议校验回真实仓库，不是空安利

广告 · 桥上

卖注意力

原生推广卡、场景栏目冠名、创作者加速位。用户本来就在挑工具，这是高意图库存。标明推广，不买断排序，不裁剪免费 Feed。

知识付费 · 过桥后

卖解决方案

场景包不是 Skill 清单，是「装上就能做成一件岗位上的事」。生活工作提效：纪要 → 待办 → 周报。过不了冷用户十分钟第一胜，不上付款页。
